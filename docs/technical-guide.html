Lead Management and Automation System · proof of concept

Lead Manager Handbook

A partner sends us sales leads over HTTP. We check that each request really came from them, store every lead once, track it through the deal stages, and copy it into a Google Sheet that stays signed in.

What it does, in five lines

  • Receives leads at POST /v1/leads with an id, name, email, company and source.
  • Rejects forged requests. Every request carries an HMAC signature made with a secret only we and the partner know.
  • Never duplicates. If the id or the email is already stored, the existing lead is updated instead of creating a second one.
  • Tracks deal stages in Postgres: New, Qualified, Proposal, then Won or Lost.
  • Mirrors every lead into Google Sheets after each add or update, using a Google sign-in done once by an admin.

Built with Go 1.26, the Fiber web framework, PostgreSQL 17 and the official Google Sheets client. Everything runs in Docker containers.

Installing Docker: follow docs.docker.com/engine/install. On Linux, then run sudo usermod -aG docker $USER and log out and back in, so Docker runs without sudo.

Using Podman instead? The Makefile falls back to Podman when Docker is not installed. The tests then reach Podman through its Docker-compatible socket; turn it on once with systemctl --user enable --now podman.socket.

Create the Google OAuth client (one time)

The app needs its own "OAuth client" so Google knows who is asking for access.

  1. Open Google Cloud console and create or pick a project.
  2. Under APIs & Services → Library, enable Google Sheets API and Google Drive API.
  3. Under OAuth consent screen, choose External, fill in the app name and your email, and add the Google account that will own the sheet as a test user.
  4. Under Credentials → Create credentials → OAuth client ID, pick Web application and add this redirect URI: http://localhost:8080/auth/google/callback
  5. Download the JSON. It is named client_secret_….json. Put it in the project root. Git ignores it.

Never commit that JSON or the .env file. Both hold secrets. .gitignore already covers them; check git status before every commit anyway.

Install and run

  1. Clone the repo 
    git clone https://github.com/kryst-alt/tech_task-1.git
cd tech_task-1
  2. Run setup

    Checks your tools, creates .env from .env.example, generates the three secrets, and copies the Google client id and secret out of the JSON. It is safe to run again: it only fills values that are empty.

    make setup
  3. Start everything

    Builds both service images and starts three containers: db, lead-api and sheets-sync. The first build downloads Go modules and takes a few minutes.

    make up
make ps   # all three should say "healthy" or "running"
  4. Link Google (one time)

    Open the sign-in link that make setup printed. It looks like this:

    http://localhost:8080/auth/google?key=<ADMIN_API_KEY from .env>

    Sign in with the test-user account and allow access. You land on a page that says Connected <email>. Leads sync to <sheet link>. The spreadsheet is named Leads and lives in that account's Drive.

  5. Send a lead

    The helper script signs the request exactly like the partner would.

    scripts/send-lead.sh '{"id":"p-1","name":"Ada","email":"ada@example.com","company":"Acme","source":"partner"}'

    You get 201 and "result":"create". Within a couple of seconds a row appears in the sheet.

  6. Check health 
    curl localhost:8080/healthz
# {"database":"ok","google":"ok"}

To stop: make down. Data stays in a container volume, so the next make up picks up where you left off, Google link included.

Common tasks

Update a lead. Send the same id or email again with different fields. You get 200 and "result":"update", and the same row in the sheet is rewritten.

Move a lead to the next stage.

curl -X PATCH localhost:8080/v1/leads/p-1/stage \
  -H "Authorization: Bearer $(grep ^ADMIN_API_KEY= .env | cut -d= -f2-)" \
  -d '{"stage":"qualified"}'

See a forged request get rejected. Pass a wrong secret as the second argument:

scripts/send-lead.sh '{"id":"p-2","name":"Eve","email":"eve@example.com","company":"X","source":"web"}' wrong-secret
# HTTP 401

Look inside the database.

docker compose exec db psql -U leads -c 'select external_id, email, stage, version from leads'

Running without containers

Handy when you are changing Go code and want fast restarts. Postgres still runs in a container.

make db-up
make run-api    # terminal 1
make run-sync   # terminal 2

Both commands load .env first. Each service applies database migrations on start-up, so there is no separate migrate step. If both start together, a Postgres lock makes one wait for the other.

Deploying beyond your laptop

The project is a proof of concept and has only been run locally. Moving it to a server needs these changes:

  1. Postgres. Point DATABASE_URL at a managed or self-hosted Postgres 15+ (Neon, Supabase and Render all have free tiers). The citext extension must be allowed.
  2. Images. Build the two images from services/lead-api/Dockerfile and services/sheets-sync/Dockerfile (build context is the repo root) and run them anywhere that runs containers. Run exactly one sheets-sync.
  3. HTTPS and redirect URL. Put lead-api behind HTTPS. Set GOOGLE_REDIRECT_URL to https://your-host/auth/google/callback and add the same URL to the OAuth client in Google Cloud.
  4. Secrets. Pass the values from .env as environment variables through the host's secret store. Give the partner LEAD_SIGNING_SECRET over a private channel.
  5. Publish the consent screen. While it is in Testing, Google expires the refresh token after 7 days and someone must sign in again. Publishing removes that limit.

Part 2 · How it works

The two services

The system is two small programs that share one database. They never call each other.

Why two services and not more

  • The partner never waits for Google. Google can be slow or down. lead-api saves the lead and answers in milliseconds; sheets-sync deals with Google on its own time.
  • Nothing is lost if one side is down. If sheets-sync stops, leads pile up in the queue and sync when it comes back. If lead-api stops, sheets-sync finishes what is queued.
  • No more than two, because splitting further (a separate "stages" service, a separate "auth" service) would add a network call to every request and buy nothing at this size.

Flow: a lead arrives

What happens, in order, when the partner calls POST /v1/leads.

  1. partnerBuilds the JSON body, takes the current Unix time, and computes HMAC-SHA256(secret, timestamp + "." + body). Sends the body with X-Timestamp and X-Signature: sha256=<hex>.
  2. lead-apiRejects with 401 if the timestamp is more than 5 minutes off (stops replays of old requests) or the signature does not match. The check runs on the raw bytes received, before any parsing.
  3. lead-apiParses the JSON, trims spaces, checks all five fields are present and the email is valid. Otherwise 422.
  4. storeOpens a transaction and locks any stored lead with the same id and any with the same email (email comparison ignores case).
  5. lead.DecideNo match: create. Match with identical fields: unchanged. Match with different fields: update. Id matches one lead and email another: conflict, 409.
  6. storeInserts or updates the row, adds 1 to its version, and makes sure it has a lead_sync row. Commits.
  7. lead-apiAnswers 201 for create or 200 for update and unchanged. Google is not involved yet.

Two identical requests at the same moment? Both may see "no match" and both try to insert. Postgres's unique index lets one win; the other gets a unique-violation error, and the store retries once. On the retry it finds the lead and turns into an update. A test forces this exact race.

Flow: syncing to Sheets

sheets-sync repeats this loop every SYNC_INTERVAL (2 seconds by default).

  1. find workSelects up to 50 leads whose version is greater than lead_sync.synced_version and whose retry time has passed.
  2. get sheetLoads the Google credentials, decrypts the refresh token, and creates the "Leads" spreadsheet with its header row if there is none yet. If nobody has linked Google, it waits quietly.
  3. write rowReads column A to find the lead's row by id. Rewrites that row if found, appends a new one otherwise. Columns: Lead ID, Name, Email, Company, Source, Stage, Created, Updated.
  4. successSets synced_version to the version just written. If the lead changed again in the meantime, its version is now higher, so the next loop picks it up.
  5. failureRecords the error and waits before retrying: 2 s, 4 s, 8 s and so on, never more than 15 minutes. Other leads keep syncing.
  6. access revokedIf Google answers invalid_grant, the link is marked needs_reauth, /healthz shows reauth_required, and syncing waits until an admin signs in again. Queued leads are not lost.

No database transaction is held open while talking to Google, so a slow Google never blocks new leads from being saved. A test checks this.

Flow: Google sign-in

Done once by an admin. After that the app keeps itself signed in.

  1. adminOpens /auth/google?key=<ADMIN_API_KEY>. The key is in the URL because a browser link cannot send an Authorization header.
  2. lead-apiSets a random state cookie and redirects to Google, asking for offline access (so Google returns a refresh token) and the drive.file scope (the app can only see files it created).
  3. GoogleShows the consent screen, then redirects back to /auth/google/callback with a one-time code and the same state.
  4. lead-apiChecks state matches the cookie (blocks forged callbacks), trades the code for tokens, and reads the account email.
  5. lead-apiEncrypts the refresh token with AES-256-GCM using TOKEN_ENCRYPTION_KEY and saves it. If a different account is linked, it forgets the old sheet and queues every lead for the new one.
  6. sheets-syncFrom then on, uses the refresh token to get a fresh access token whenever the old one expires (about every hour). No browser needed.

The database

Three tables. The schema lives in db/migrations/.

At most one row. Holds the linked account email, the encrypted refresh token, the spreadsheet id, and the needs_reauth flag.

Deal stages

new→qualified→proposal→won

From any of new, qualified or proposal a lead can also move to lost. won and lost are final. Skipping a stage or going backwards returns 409. Leads sent by the partner never change the stage; only the admin endpoint does.

Concepts explained

HMAC signature

A fingerprint of the message made with a shared secret. Anyone can read the body, but without the secret nobody can produce a fingerprint that matches it. Changing one character of the body changes the fingerprint completely. The timestamp is part of what gets signed, so an attacker cannot resend an old request later. We compare fingerprints with hmac.Equal, which takes the same time whether the first or last byte differs, so timing gives nothing away.

Upsert

"Update or insert." Look for an existing record; update it if found, insert it if not. Here a match can come from either the id or the email.

Row locks and transactions

SELECT … FOR UPDATE inside a transaction stops two requests from editing the same lead at once. The second waits until the first commits.

Version numbers instead of a message queue

Rather than pushing "sync this" messages somewhere, each lead has a counter. The worker syncs any lead whose counter is ahead of what it last wrote. Ten quick edits to one lead become one sheet write of the latest data.

Exponential backoff

After each failure, wait twice as long as last time before retrying. It stops a broken Google connection from being hammered. The cap keeps the wait reasonable.

OAuth refresh tokens

An access token lets the app call Google for about an hour. A refresh token lets it get new access tokens without a person signing in. We store the refresh token encrypted, so a database leak alone does not hand out access to the Google account.

sqlc

You write plain SQL in db/queries/*.sql; make generate turns each query into a typed Go function in internal/store. Typos in column names fail at generate time, not in production.

Migrations with goose

Each file in db/migrations is one schema change. goose records which ones have run and applies the rest at start-up. Never edit a migration that has already run; add a new file instead.

Testcontainers

Tests start a real Postgres in a container, run, and throw it away. Tests hit the same database engine as production, so there are no fake database objects to keep in sync.

Tests

make check                             # Go + acceptance tests, readable report
scripts/test.sh stages                 # one area in both suites
make test                              # Go tests only
go test ./internal/lead/...            # one package, no database needed
go test ./services/lead-api/api -run TestDuplicateSubmission -v   # one test by name

The Go tests start their own Postgres container, so they never touch your dev data. The acceptance tests in tests/acceptance/ are different: they are written in Python with pytest and test the running system from outside, the way a QA tester would. They send real signed requests, read Postgres to check what was stored, and wait for sheets-sync to write each change to the real sheet. Their lead IDs start with qa-.

Making a change

  1. Write a failing test first

    Put it next to the code you will change. Run it and watch it fail for the reason you expect.

  2. Make the smallest change that passes

    Changing SQL? Edit db/queries, run make generate. Changing the schema? Add a new file in db/migrations.

  3. Run the whole suite

    make check (with make up running), then gofmt -l . should print nothing.

  4. Try it for real

    make up, send a lead with scripts/send-lead.sh, look at the sheet.

  5. Update the docs

    New setting: add it to .env.example and the README. New design decision: note it in docs/STACK.md.

The repo is set up for Neovim with gopls, but any editor with Go support works.

Troubleshooting

SymptomCause and fix
Tests fail with "Cannot connect to the Docker daemon"Docker is not running or your user can't reach it: sudo systemctl enable --now docker and make sure you are in the docker group (groups). "permission denied" on docker.sock right after joining the group means the session is older than the change: log out and back in. With Podman: systemctl --user enable --now podman.socket
make up says port 8080 or 5432 is in useSomething else holds it. Set PORT or DB_PORT in .env. If you change PORT, update the redirect URI in Google Cloud too.
Every lead gets 401The sender and .env use different secrets, or the clock is more than 5 minutes off. The body must be signed byte for byte as sent.
Google says redirect_uri_mismatchThe URL in Google Cloud must match GOOGLE_REDIRECT_URL exactly, port included.
Google says "access blocked" or "app not verified"The account is not a test user on the consent screen. Add it, or click through the unverified warning for your own app.
/healthz shows not_linkedNobody has signed in yet. Open the /auth/google?key=… link.
/healthz shows reauth_requiredGoogle revoked the token (7-day limit in Testing, or access removed). Sign in again with the same link; queued leads then sync.
Rows appear slowly during a bulk importGoogle's per-minute limit. Failed writes retry with backoff and catch up.
A service exits right after startRun make logs. A config error lists every bad variable.

Limits and next steps

All requirements in docs/PROJECT.md are done and tested. These are the known gaps, roughly in the order worth tackling:

  1. Google token lifetime. The consent screen is in Testing, so the refresh token expires after 7 days. Publish the app before real use.
  2. Sheets API quota. Each lead costs two Google calls (find the row, write it). Reading column A once per batch would halve that for bulk imports.
  3. No rate limiting or request logging on the public endpoint. Add both before exposing it to the internet.
  4. Rotated refresh tokens are not saved. Google rarely rotates them for this kind of app, but saving a new one when it appears would remove the risk.
  5. Hosting. Only run locally so far. See Deploying beyond your laptop.

Glossary

Lead
A potential customer: a person, their email, their company, and where they came from.
Partner
The outside system that sends us leads.
Deal stage
How far a lead is in the sales process.
Fiber
The Go web framework used for lead-api.
pgx
The Go driver that talks to Postgres.
Compose
A file (compose.yaml) that starts several containers together.
Healthcheck
A command the container runtime runs to see if a service is alive. Here it calls /healthz.
OAuth client
The id and secret that identify this app to Google.
Consent screen
The Google page that asks the user to allow access.
Scope
What the app is allowed to do in the Google account. Ours can only touch files it created.
AES-256-GCM
The encryption used for the stored refresh token. It also detects tampering.
Advisory lock
A named Postgres lock. Used so two services starting together don't run migrations twice.
